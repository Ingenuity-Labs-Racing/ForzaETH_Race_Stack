# State machine

ROS 2 Humble package that selects a driving behavior and publishes the local waypoint window. The controller manager receives that behavior and computes speed and steering commands.

Controller selection is independent of behavior: MAP, PP, AGMPC, NMPC, and FTG are selected on the controller side. Adding a tracking controller does not require a new state such as `AGMPC_TRACK`.

## Organization

| File | Responsibility |
| --- | --- |
| [state_machine/state_machine.py](state_machine/state_machine.py) | ROS node, subscriptions, publishers, condition checks, parameter handling, and control-loop timer. Includes `StateMachineParams`. |
| [state_machine/behavior.py](state_machine/behavior.py) | `StateType`, state parsing, waypoint selection, and transition functions. |
| [launch/state_machine_launch.xml](launch/state_machine_launch.xml) | State-machine launch arguments and parameter loading. |

## Behaviors and waypoints

| Behavior | Published index | Local waypoint source |
| --- | --- | --- |
| `GB_TRACK` | 0 | Window from the scaled global raceline. |
| `TRAILING` | 1 | Cached avoidance spline when available; otherwise the scaled global raceline. |
| `OVERTAKE` | 2 | Window from the path returned by `get_splini_wpts()`, using the cached avoidance spline. |
| `FTGONLY` | 3 | No waypoint window; commands are generated by the reactive controller. |

For global tracking, the first index is computed from Frenet distance:

```python
index = int(cur_s / waypoints_dist + 0.5)
```

The node selects `n_loc_wpnts` consecutive waypoints and wraps indices around the track. This selection uses distance along the global raceline. Any time-based reference sampling needed by AGMPC or NMPC happens inside the controller.

Waypoint positions, headings, and desired speeds come from the selected path. The state machine does not solve an optimization problem or calculate steering commands. Upstream speed scaling is already present in `/global_waypoints_scaled`.

In `FTGONLY`, the waypoint selector returns an empty list. The node logs a warning and suppresses publication of an empty `WpntArray`; it continues publishing the behavior and visualization messages.

## Modes and transitions

- `timetrials`: selects `GB_TRACK` every cycle.
- `head_to_head`: selects among the four behaviors using obstacle clearance, distance from the raceline, overtaking-sector permissions, and avoidance-spline availability.
- `dummy`: legacy transition path. It still references a removed `LOW_BAT` state and should not be used as a working low-battery behavior.

In head-to-head operation, a blocked global corridor leads to trailing. Overtaking requires an allowed sector, an available spline, and a clear spline corridor. The node returns to global tracking when the relevant clearance and raceline conditions are met. FTG-only zones select `FTGONLY`.

The stuck-vehicle FTG condition exists, but `ftg_disabled = True` currently disables that trigger. FTG-only zone transitions are separate from this trigger.

With `force_state: true`, `force_state_choice` overrides the mode's transition result. Its default is `GB_TRACK`; accepted values are the four behavior names above. An `initial_state` alone does not override subsequent transitions.

## Running

Run these commands in the ROS container after sourcing the built workspace:

```bash
source ~/ws/install/setup.bash
```

For a normal simulation run, first start the simulator and its base stack, then launch the controller and state machine:

```bash
ros2 launch stack_master time_trials_launch.xml \
  racecar_version:=SIM ctrl_algo:=AGMPC test_on_car:=False
```

Change `ctrl_algo` to select the controller. See the [controller guide](../controller/README.md) for configuration and registration details.

To launch only the state machine, with the upstream nodes already running:

```bash
ros2 launch state_machine state_machine_launch.xml \
  mode:=timetrials test_on_car:=False
```

This standalone launch does not start a simulator, planner, or controller.

For the headless two-lap tuning workflow:

```bash
ros2 launch stack_master controller_tuning.launch.py
```

Select the map, controller, and inline controller tuning in [evaluation/tuning_params.yaml](../controller/evaluation/tuning_params.yaml). That workflow starts the simulation stack without RViz; see the [evaluation guide](../controller/evaluation/README.md).

### State-machine launch arguments

| Argument | Default | Purpose |
| --- | --- | --- |
| `mode` | `timetrials` | Transition mode. |
| `initial_state` | `GB_TRACK` | Initial driving behavior. |
| `test_on_car` | `True` | Enable VESC battery subscription; set false for simulation. |
| `overtake_mode` | `spliner` | Avoidance-path mode. |
| `log-level` | `debug` | Node logging level. |
| `param_file` | Installed `stack_master/config/state_machine_params.yaml` | ROS parameter file. |

Explicit launch parameter values override the corresponding values loaded from `param_file`.

## Parameters

The [normal-stack YAML](../stack_master/config/state_machine_params.yaml) contains these behavior-related settings:

| Parameter | Default | Meaning |
| --- | --- | --- |
| `rate_hz` | 40 | State-machine loop frequency in Hz. |
| `n_loc_wpnts` | 80 | Number of waypoints in the local window. |
| `initial_state` | `GB_TRACK` | Initial behavior. |
| `test_on_car` | `True` | Enable battery feedback from VESC. |
| `force_state` | `False` | Override transition logic using `force_state_choice`. |
| `overtake_mode` | `spliner` | Avoidance-path mode. |
| `volt_threshold` | 11.0 | Low-battery threshold in V; not a working emergency-stop behavior. |
| `gb_ego_width_m` | 0.4 | Raceline rejoining tolerance in m. |
| `lateral_width_gb_m` | 1.1 | Lateral obstacle tolerance around the global path in m. |
| `gb_horizon_m` | 6.9 | Global-path obstacle-check horizon in m. |
| `overtaking_horizon_m` | 6.9 | Overtaking obstacle-check horizon in m. |
| `lateral_width_ot_m` | 0.3 | Lateral obstacle tolerance around the overtaking path in m. |
| `splini_ttl` | 2.0 | Cached avoidance-path lifetime in s. |
| `splini_hyst_timer_sec` | 0.2 | Hysteresis when changing overtaking side, in s. |
| `ftg_threshold_speed` | 0.1 | Speed threshold in m/s for the currently disabled stuck-vehicle FTG trigger. |
| `ftg_timer_sec` | 3.0 | Duration below that threshold, in s. |

`force_state_choice` is declared by the node with default `GB_TRACK`, although it is absent from the default YAML.

The same YAML also contains FTG algorithm settings: `debug`, `safety_radius`, `max_lidar_dist`, `range_offset`, `track_width`, and `max_speed`. The controller manager reads these for the FTG controller in normal operation. They are separate from state-transition logic. The evaluation workflow instead allows FTG tuning in its `controllers.FTG` block.

## ROS interfaces

Topic names below assume the default root namespace. Publishers use relative names and follow the node namespace when one is applied. Subscription and publisher queue depth is 10.

### Inputs

| Topic | Message type | Use |
| --- | --- | --- |
| `/global_waypoints` | `f110_msgs/msg/WpntArray` | Global path information and maximum reference speed. |
| `/global_waypoints_scaled` | `f110_msgs/msg/WpntArray` | Global path after speed scaling; source for global tracking. |
| `/car_state/frenet/odom` | `nav_msgs/msg/Odometry` | Vehicle progress and lateral position in Frenet coordinates. |
| `/car_state/pose` | `geometry_msgs/msg/PoseStamped` | Vehicle pose; subscribed in head-to-head mode. |
| `/planner/avoidance/otwpnts` | `f110_msgs/msg/OTWpntArray` | Avoidance spline; subscribed in head-to-head mode. |
| `/perception/obstacles` | `f110_msgs/msg/ObstacleArray` | Obstacles; subscribed in head-to-head mode. |
| `/vesc/sensors/core` | `vesc_msgs/msg/VescStateStamped` | Battery voltage when `test_on_car` is true. |

Startup waits for global waypoints, scaled global waypoints, and Frenet odometry. Head-to-head mode also waits for pose. The node obtains overtaking-sector parameters through `/ot_interpolator/get_parameters`, so that service must be available.

### Outputs

| Topic | Message type | Content |
| --- | --- | --- |
| `/state` | `std_msgs/msg/String` | Behavior serialized as, for example, `StateType.GB_TRACK`. |
| `/state_idx` | `std_msgs/msg/Int8` | Behavior index from the table above. |
| `/local_waypoints` | `f110_msgs/msg/WpntArray` | Selected local path in the `map` frame. |
| `/local_waypoints/markers` | `visualization_msgs/msg/MarkerArray` | Local-path visualization. |
| `/state_marker` | `visualization_msgs/msg/Marker` | Current behavior visualization. |

There is no active emergency-braking output or state-machine latency publisher in the current node.

## Adding a controller or a behavior

For a new controller that follows the existing path, implement its adapter and register it in the [controller registry](../controller/core/controller_registry.py). Declare its required inputs and supported behaviors there. Keep `GB_TRACK` for global-path tracking.

Currently MAP and PP support `GB_TRACK`, `TRAILING`, and `OVERTAKE`, with an explicit FTG fallback for `FTGONLY`. AGMPC and NMPC support `GB_TRACK` only; the manager stops on unsupported behaviors. Selecting FTG directly uses its reactive LiDAR algorithm.

Only a new driving behavior requires state-machine changes: add its enum, waypoint selection, and transitions in `behavior.py`, then update the node's behavior index and visualization handling as needed. Update this README alongside those changes.
